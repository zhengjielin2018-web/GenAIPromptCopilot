# 單輪流程說明：一段中文描述如何變成生圖提示詞

日期：2026-09-22
對應程式：[`scripts/demo.py`](../scripts/demo.py)、[`scripts/pipeline/retrieval.py`](../scripts/pipeline/retrieval.py)、[`scripts/demo_render.py`](../scripts/demo_render.py)

> **維護規則：這份文件跟著程式走。**
> 只要動到 `demo.py` 的兩個 prompt template、`AnalysisResult`／`AssemblyResult` schema、
> 兩個 `validate_*` 函式，或 `retrieval.py` 的檢索、去重、分級邏輯，
> 這份文件必須在同一個 commit 裡一起更新。文件裡的範例輸出若已與現況不符，重跑一次補上新的。

## 0. 先講清楚範圍

現在能跑的是 **`scripts/demo.py`：單輪、不追問**。你給一段中文，它一次做完分析、檢索、組裝，
印出提示詞與建議，結束。

規格書裡那個會反問你、有 session 狀態機、由 LLM 自己決定要追問還是定稿的 SK agent，
是**子專案 2，尚未開始**。這份文件不描述它。

一次執行會打 **3 次 Gemini**：分析（結構化生成）、向量化（一次 `embed_batch` 涵蓋全部查詢）、組裝（結構化生成）。

## 3. 步驟 ①：分析

### 丟進去什麼

`ANALYSIS_TEMPLATE` + 完整 facet 清單（含每個 facet 的中文標籤與英文提示例）+ 使用者原句。

### 要求回什麼

Pydantic schema `AnalysisResult`，由 Gemini 的結構化輸出保證形狀：

```python
class AnalysisResult(BaseModel):
    subject_profile: Profile          # portrait | landscape | object | vehicle
    facets: list[FacetAssessment]     # facet_id + state
    queries: list[SubQuery]           # dimension + 繁中查詢語句
```

三件事，prompt 裡寫得很死：

1. **判題材**。動物歸 `object`（這是子專案 1 執行時踩過才定的，不是直覺）。
2. **每一個 facet 都要判**，一個都不能漏，三態：
   - `covered` — 使用者已經提供這項資訊
   - `missing` — 這項對本題材有意義，但使用者沒提
   - `notApplicable` — 這項對本題材根本不適用（風景沒有「人物穿著」）
3. **產生分維度子查詢**，規則不同：
   - 有任一 facet `covered` 的維度 → 給 **1 句，逐字用使用者原話**，不准改寫、不准補充
   - 整個維度都 `missing` → 給 **2 句，方向必須對比**（「寫實攝影」對「動漫插畫」），不是同方向的兩種說法
   - 整個維度都 `notApplicable` → 不給

### 實際回了什麼

```text
題材 portrait
子查詢：場景「霓虹街頭」 人物樣貌「銀髮少女」 人物動作「抬頭看著天空」
       推想：風格「精緻的寫實攝影風格，呈現逼真的光影與質感」
             風格「精美的日系動漫插畫風格，筆觸細膩色彩鮮明」
             鏡頭「特寫鏡頭突顯人物情緒與臉部表情」
             鏡頭「廣角全景鏡頭展現宏大的環境空間感」
             人物穿著「時尚現代的潮流服飾與精緻配件」
             人物穿著「簡約舒適的日常休閒穿搭」
```

看得出兩條路徑：**前三個維度是原話切片**（「霓虹街頭」「銀髮少女」「抬頭看著天空」都是原句裡的字），
**後三個維度是推想，而且成對出現**（寫實／動漫、特寫／廣角、時尚／休閒）。

### 為什麼要這樣分

- **covered 用原話不准改寫**：查詢向量要貼近使用者真正說的東西。LLM 一改寫就會摻進它自己的偏好，
  檢索出來的東西就不再是「你要的」而是「它以為你要的」。
- **missing 給對比兩句**：使用者沒說的維度，不撈就什麼建議都沒有；只撈一個方向等於幫使用者做了決定。
  給對比的兩句，至少建議清單會呈現兩個不同選項讓使用者挑。

## 4. 步驟 ①.5：Python 接手整理

LLM 回來後，Python 做三件事，全部是**不信任 LLM 自述**的設計。

### `facet_state_map()` — 補漏、去雜

只留這個 profile 適用的 facet；**LLM 漏判的一律補成 `missing`**。

保守方向是刻意的：寧可多報一個「缺」讓使用者看到，也不要假裝某項已經有了而靜靜略過。

### `grounded_dimensions()` — 自己推，不問 LLM

一個維度算不算「使用者有講」（`grounded`），是**從 facet 狀態推導的**，不是 LLM 回報的欄位：

```python
{catalog.dimension_of(fid) for fid, s in states.items() if s == "covered"}
```

本例推出 `{scene, appearance, pose}`。這個值後面決定「片段可不可以借進提示詞」，
是整個流程裡權限最大的一個 flag——所以**不能讓 LLM 有機會捏造它**。少一個可被捏造的欄位，就少一種失控方式。

### `normalize_queries()` — 清洗子查詢

| 情況 | 處理 |
| :--- | :--- |
| 維度不屬於這個 profile | 丟掉 |
| query 是空白 | 丟掉 |
| grounded 維度給超過 1 句 | 只留第一句 |
| missing 維度給超過 2 句 | 只留前兩句 |
| **grounded 維度一句都沒給** | **用整句描述頂上** |

最後一條是防呆：LLM 偶爾會漏掉某個維度的查詢，但那個維度使用者明明講了。
一次漏答不該讓整個維度完全沒東西可撈，所以退而求其次用整句頂著。

每個維度也在這裡決定撈幾筆：grounded 的 `k=5`、missing 的每句 `k=3`。

## 5. 步驟 ②：檢索

### 先一次把向量算完

```python
vectors = client.embed_batch([整句] + [每一句子查詢], task_type="RETRIEVAL_QUERY")
```

本例是 1 句整句 + 9 句子查詢 = **10 個向量，一次呼叫**。整句向量給「相似作品」用，子查詢向量給 preset 用。

### 每一句子查詢各跑一次 SQL

```sql
SELECT id, title, category, facet_ids, prompt_snippet, negative_snippet,
       preset_embedding <=> %(q)s AS dist
FROM prompt_knowledge_presets
WHERE facet_ids && %(facets)s          -- GIN 索引，過濾出「這個維度」的候選池
ORDER BY dist                          -- HNSW 索引，用「這一句自己的向量」排序
LIMIT %(k)s
```

**這裡是整個設計的核心：每個維度用自己的查詢向量，而不是拿整句去撈。**

實測（2026-09-22）：同樣過濾到 Style 候選池，
用整句描述的向量排序撈回無關片段（dist **0.354**），
用該維度專屬語句撈回正確的風格片段（**0.229–0.234**）。

原因是單一整句向量是六個維度的模糊平均，只會貼近最泛用的片段；
而且使用者沒提到的維度，整句向量裡根本沒有對應的訊號，永遠撈不到。

### 同時撈候選池大小

```sql
SELECT count(*) FROM prompt_knowledge_presets WHERE facet_ids && %(facets)s
```

本例：

```text
風格 池 4455 → 6（高 6）  場景 池 6752 → 5（高 5）  鏡頭 池 2147 → 6（高 6）
人物樣貌 池 3617 → 5（高 5）  人物動作 池 2494 → 5（中 5）  人物穿著 池 2287 → 6（高 6）
相似作品 3（portrait）
```

> 池子大小會隨語料庫變動；要看當下真實的數字，跑 `python coverage_report.py`。

「池 N → M」是**分維度檢索最有價值的副產品**：它讓知識庫的覆蓋缺口在使用當下就看得見。
例如換成 vehicle 題材時，「人物動作 池 2」會直接印在畫面上——不必事後去查資料庫才發現那個維度幾乎是空的。

### 分級，不設門檻

```python
dist < 0.25 → 高     dist < 0.30 → 中     其餘 → 低
```

**刻意不設距離門檻把低分的濾掉**，而是分級後全部交給 ③ 判斷。
本例六個維度裡最弱的是「人物動作」，五筆全在「中」（0.264–0.274）。

> 這一段本身就是語料量的實證。**資料庫擴增前**（859 筆 presets），同一句查詢的
> 「人物動作」五筆全是「低」（0.304–0.361），設門檻就會讓整個維度變空——不設門檻
> 才救得回來。擴增到 18,977 筆後同一個維度升到「中」，其餘五個維度全部是「高」。
> 門檻沒有改，改變的是候選池裡真的有更貼近的片段可選。

### 跨維度去重

一筆 preset 的 `facet_ids` 可能橫跨數維（18,977 筆裡有 3,076 筆、16.2%），會同時出現在多個候選池。
（擴增前是 859 筆裡 134 筆、15.6%——比例幾乎沒變，可見這是 LLM 標註片段的習性，不是語料量的函數。）
只留一筆，歸屬規則是 **grounded 優先、距離次之**：

1. 有任何 grounded 維度撈到它 → 歸給這些維度中距離最小的那個
2. 完全沒有 grounded 維度撈到 → 才退回全體最小距離

不能單純比距離，因為**歸屬決定借用資格**。`grounded` 是「這個維度使用者講了沒」的屬性，
不是片段的屬性；單純比距離的話，一個 grounded 維度正當撈到的片段，
會因為某個 missing 維度**推想出來**的查詢剛好更近，就被降級成「僅供建議」而失去借用資格。

本例六個維度共撈回 33 筆，去重後仍是 33 筆——這一次沒有任何片段跨維度重複。
（擴增前同一句查詢會撞到一筆重複，合併成 32 筆。命不命中純看候選內容，機制本身照跑。）

### 標註 facet 覆蓋

`annotate_coverage()` 對每筆候選的每個 `facet_id`，填上「這一項對**本次使用者**是 covered 還是 missing」。
這是給 ③ 看的，例如：

```text
[中 0.264] id=7879 草地仰望星空  可借入
    facets: pose.main=missing, pose.gaze=covered
    lying on the grass with her hands behind her head, gazing at the starry sky
```

意思是：這個片段你可以借，但它涉及兩個 facet——
`gaze`（仰望）是使用者講過的、`main`（躺在草地上）是使用者沒講的。
所以 `gazing at the ...` 這半段可以借，`lying on the grass with her hands behind her head`
**不行**——使用者說的是站在街頭，不是躺在草地上。

### 另外撈相似作品

用**整句**向量 + profile 過濾，從 `shared_prompt_histories` 撈 3 筆完整的既有作品，
給 ③ 當風格參考（prompt 裡明講「不要照抄」）。

## 6. 步驟 ③：組裝

### 丟進去什麼

`ASSEMBLY_TEMPLATE` + 題材 + facet 狀態表 + **分維度排好並標註過的候選片段** + 相似作品 + 使用者原句。

候選片段長成上面 `id=7879` 那個樣子：有分級、有「可借入／僅供建議」、有每個 facet 的 covered/missing。

### Prompt 裡的硬規則

1. 使用者已描述的內容必須**完整**反映在提示詞裡。
2. **複合屬性用複合 tag 完整表達**（雙色髮、漸層這類）——要寫成 `split-color hair, two-tone hair, purple hair, pink hair`
   這種能讓生圖模型理解結構的組合，不可被片段裡的單色詞吃掉一半；知識庫沒有的詞自己翻譯。
   （這條附了「範例中的詞本身不可原封抄進提示詞」的但書，因為實測會被照抄。）
3. 標為 `missing` 的 facet **不要自行發明**，留白給生圖模型；基礎畫質詞與基礎負向詞例外。
4. 「僅供建議」的片段一個字都不准進提示詞；「可借入」的片段，其中標 `missing` 的 facet 對應的詞也不准進。
   相似度「低」的片段仍可借用其中與描述相符的詞。
5. `borrowed` 只列**真的寫進提示詞**且**真的來自該片段**的詞。
6. `suggestions`：每個有 missing facet 的維度都要給一則，2–3 個**不同方向**的選項。

### 要求回什麼

```python
class AssemblyResult(BaseModel):
    positive_prompt: str                    # 英文，逗號分隔 tag
    negative_prompt: str
    borrowed: list[BorrowedFrom]            # preset_id + 宣稱借用的 tags
    suggestions: list[DimensionSuggestion]  # dimension + missing_labels + options
```

### 實際回了什麼

```text
正向：1girl, solo, white hair, long hair, streets of a cybernetic Tokyo,
      night, rain, neon lights, looking up at the sky

負向：lowres, bad anatomy, bad hands, text, error, missing fingers, extra digit,
      fewer digits, cropped, worst quality, low quality, normal quality,
      jpeg artifacts, signature, watermark, username, blurry
```

對照一下使用者原句——「銀髮」→ `white hair`、「少女」→ `1girl`、
「雨夜的霓虹街頭」→ `streets of a cybernetic Tokyo, night, rain, neon lights`、
「抬頭看著天空」→ `looking up at the sky`。**風格、鏡頭、穿著三個維度完全空白**，沒有自行發明，符合規則 3。

## 7. 步驟 ③.5：Python 驗證

這是整個流程裡最值得看的一段：**不信 LLM 對自己行為的描述**。

### `validate_borrowed()` — 兩道獨立檢查

對每一筆宣稱的借用：

1. preset 在本次檢索結果內嗎？不在 → 整筆不計
2. 這個 preset 的歸屬維度 `grounded` 嗎？不是 → 整筆降級成建議
3. 對每個 tag：
   - **來源檢查**：這個詞真的出現在片段原文裡嗎？
   - **使用檢查**：這個詞真的出現在最終提示詞裡嗎？

兩邊都中才算數。

### 實際被擋下來的

> 下面這段是**擴增前**那次執行的輸出，刻意保留：擴增後同一句查詢**一筆都沒有被擋下**
> （四筆借用全部通過來源與使用檢查），所以新的輸出沒辦法示範這個機制。程式碼裡的
> `validate_borrowed()` 沒有變，只是這次沒踩到。本次的借用結果是：
>
> ```text
> [高 0.197] 銀髮精靈少女（Appearance）→ 借入 1girl, solo, silver hair
> [高 0.218] 霓虹雨夜街道（Scene）→ 借入 rainy city street with neon signs in Japanese
> [高 0.210] 霓虹夜景（Scene）→ 借入 neon city background, city background, night
> [中 0.267] 仰望星空（Pose）→ 借入 looking up, raised head
> ```

```text
借用的知識庫片段
  [高 0.242] 銀髮動漫少女（Appearance）→ 借入 white hair, long hair
  [高 0.247] 雨夜霓虹城市（Scene）→ 借入 night, rain, neon lights
  [高 0.233] 霓虹賽博城市（Scene）→ 借入 streets of a cybernetic Tokyo
  [低 0.304] 雙劍望天姿勢（Pose）→ 借入 looking up at the sky
  ✗ id 907〈銀髮動漫少女〉的 "1 girl" 未出現在提示詞裡，不計入借用
  ✗ id 165〈雨夜霓虹城市〉的 "cityscape" 未出現在提示詞裡，不計入借用
```

第一個 ✗ 很典型：片段 907 的原文確實有 `1 girl`（有空格），LLM 也確實宣稱借了它，
但它實際寫進提示詞的是 `1girl`（無空格）。來源檢查過了，使用檢查沒過，所以不計入。

第二個 ✗ 是 `cityscape`——片段 165 有這個詞，但最終提示詞裡沒有，宣稱不成立。

另外看 `雙劍望天姿勢`：借了 `looking up at the sky`（對應 `pose.gaze=covered`），
**沒有借 `2 swords in hand`**（對應 `pose.interaction=missing`）。規則 4 被遵守了。

### 關鍵：驗證只改紀錄，不動提示詞

```python
"""驗的是「來源」不是「正確性」。只改 borrowed 紀錄，絕不動提示詞。"""
```

被拒絕的項目不會回頭去修改 `positive_prompt`。理由是：驗證器判斷的是「這個借用聲明成不成立」，
它沒有資格判斷「這個詞該不該在提示詞裡」。自動改提示詞會讓輸出變得不可預測，
而且驗證器的字面比對本來就會有誤判（見下面的限制）。

被拒的理由全部原文印出來，不吞掉。所以畫面上寫「借用了 4 個片段」是驗過的，不是 LLM 說了算。

### `validate_suggestions()`

- 這個維度其實沒有任何 missing facet → 整則移除（不該有建議）
- 選項的來源 preset 不在本次檢索結果內 → 移除該選項
- `missing_labels` **一律以 ① 的判定覆寫** LLM 自己填的，不採信

注意建議的來源**不受 `grounded` 限制**——那道閘門只管提示詞。
使用者沒描述的維度，撈回來的片段本來就是要拿來給建議的。

## 9. 已知限制

誠實寫在這裡，不美化。

### facet 級的「不發明」只有 prompt 約束，沒有硬保證

上面「借了 `looking up at the sky` 但沒借 `2 swords in hand`」是 LLM 自己守了規則 4，
**程式沒有保證它會這樣**。`validate_borrowed()` 能驗「這個詞真的來自這個片段」，
但驗不了「這個詞對應的 facet 是不是使用者 missing 的那一項」——因為片段裡沒有 tag → facet 的對應欄位，
只有整筆片段層級的 `facet_ids`。

要做到硬保證，得回頭改資料管線的結構化階段，讓它多產出 tag 級的 facet 對應。另案。

### 基礎畫質詞不穩定

負向的 boilerplate（`lowres, bad anatomy, …`）和正向的畫質詞（`masterpiece, best quality`）
**完全由 prompt 規則 3 產生，程式裡沒有寫死**。

同一句輸入連跑兩次，一次產出了 `masterpiece, best quality`，一次沒有。
規格 §5.5 說「畫質詞與負向詞永遠生成」，目前的實作達不到「永遠」。要保證就得在程式裡寫死後綴。

### 借用驗證是字面比對，會少算

`"1 girl"` vs `1girl` 那個例子就是。驗證器用的是大小寫無關的子字串比對，
形式稍有出入就判不成立。方向是刻意的：寧可少算一筆借用，也不要放寬到會誤認。
反正驗證不動提示詞，少算只影響「借用了幾筆」這個統計，不影響輸出品質。

### 單輪，不追問

使用者沒描述的維度只會變成「建議」列出來，不會反問「你要 A 還是 B」。
而且「推想 2 句對比方向」本身已經隱含創作決定——推想「動漫」就只會撈到動漫的東西，
對比兩句是緩解不是解決。真正的解法是子專案 2 的追問流程。

### LLM 非決定性

同一句輸入兩次執行，① 的子查詢措辭不同（「寫實攝影風格的畫面」vs「精緻的寫實攝影風格，呈現逼真的光影與質感」），
撈回的候選也因此略有差異，最終提示詞也不完全一樣。這是預期行為，不是 bug，但做 eval 時要記得。

### Gemini 可能直接拒絕組裝這一步

步驟 ③ 送出的 prompt 含使用者描述**與**撈回的候選片段。Gemini 有時會判定這個組合不該生成，
回 HTTP 200 但 `candidates=null`、`promptFeedback.blockReason=PROHIBITED_CONTENT`。

實測（2026-09-22，每格 3 次）：「少女＋熱褲」3/6 被擋、「成年女性＋熱褲」2/6、「少女＋泳裝」2/3、
「成年女性＋泳裝」0/3；少女／男性／風景／載具配一般服裝共 0/18。**觸發因子是暴露性服裝，
不是年齡用詞**——加「成年」有幫助但不消除。步驟 ① 的分析從沒被擋過。

遇到時 `demo.py` 印一段說明並以 exit code 2 結束，不會噴 traceback：

```text
Gemini 判定這次的內容不該生成，已攔截（block_reason=PROHIBITED_CONTENT）。
      這不是程式錯誤，也不是知識庫的問題——攔截發生在把提示詞交給 Gemini 組裝的那一步。
      實測上「未成年人物＋暴露性服裝」的組合最容易觸發，換個說法再試通常就過了。
```

攔截是機率性的，實測同一份 SFW 內容也會被誤擋，所以 **`gemini_client` 對它重試一次，但只一次**：
送進去的內容是我們自己判定可接受的，容忍上游一次誤判合理；重送到通過為止則等於利用
分類器的不確定性規避安全判定。與內容無關的空回應（`MAX_TOKENS` 截斷等）則會自動重試 3 次，
呼叫端不必處理。子專案 2 的對應要求見
[多輪對話設計 §5.5](superpowers/specs/2026-09-22-multi-turn-dialogue-design.md)。
